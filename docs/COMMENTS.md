# Threaded comments

FountainJS comments are an optional, framework-neutral review module. They do
not require Yjs, React, a Fountain account, or a particular database. The
module owns portable thread data, document anchors, anchor mapping, commands,
events, validation, and editor decorations. The application owns identity,
authorization, transport, storage, notifications, and retention.

This split is deliberate: a local notebook can keep comments on the device, a
collaborative product can put them in its existing database, and a regulated
product can enforce its own access and audit policy without routing document
content through a FountainJS service.

## What is available today

- inline ranges, including ranges that cross blocks;
- zero-width point comments, whole-block comments, and document comments;
- overlapping, selected, hovered, resolved, and orphaned annotations;
- replies, text or portable rich-JSON bodies, editing, deletion, reactions,
  resolve/reopen, archive/restore, thread deletion, and reattachment;
- mapped anchors that follow ordinary transactions;
- quote/context recovery after a document replacement and a visible orphan
  state when no safe target can be recovered;
- provider-neutral connection lifecycle and atomic storage operations;
- immutable state, public events, custom permission predicates, and bounded
  validation at the browser boundary;
- an accessible optional React discussion panel; and
- a shared in-memory adapter for tests, prototypes, and offline/local products.

The package does not include a hosted comments backend. `InMemoryCommentsStore`
does not persist across a page reload. A production application supplies an
adapter backed by its own authenticated service or local persistence.

## Install and compose

The comments implementation is isolated from the root bundle:

```ts
import {
  CoreExtension,
  composeExtensions,
  createEditor,
} from 'fountainjs-editor'
import {
  InMemoryCommentsStore,
  createCommentsExtension,
} from 'fountainjs-editor/comments'

const store = new InMemoryCommentsStore()
const comments = createCommentsExtension({
  adapter: () => store.createAdapter(),
  user: { id: session.user.id, name: session.user.name },
})
const kit = composeExtensions([CoreExtension, comments])
const editor = createEditor({ schema: kit.schema, plugins: kit.plugins })
```

`adapter(editor)` must create or return the adapter instance for that editor.
The local `user.id` must be a stable application identity—not a display name.
Set `autoConnect: false` when the host needs to connect only after a room or
session is ready.

## Create and operate threads

```ts
import {
  addComment,
  createCommentThread,
  removeComment,
  selectCommentThread,
  setCommentThreadResolved,
  toggleCommentReaction,
  updateComment,
} from 'fountainjs-editor/comments'

// Uses the current text selection. A caret creates a point comment.
const thread = await createCommentThread(editor, {
  content: 'Can we cite the source?',
  data: { category: 'fact-check' },
  commentData: { mentionIds: ['user-grace'] },
})

await addComment(editor, thread.id, { content: 'Source added.' })
await toggleCommentReaction(editor, thread.id, thread.comments[0].id, '✅')
await updateComment(editor, thread.id, thread.comments[0].id, 'Please cite the primary source.')
await setCommentThreadResolved(editor, thread.id, true)
selectCommentThread(editor, thread.id)
await removeComment(editor, thread.id, thread.comments[0].id)
```

Use `type: 'block'` to target the selected node or nearest block and
`type: 'document'` for a document-level discussion. Pass an explicit Fountain
selection when the target is not the editor's current selection. Thread and
comment IDs are generated by default; a host may inject `idFactory` for its own
globally unique scheme and `now` for a trusted clock.

`CommentContent` is either a string or `NodeJSON`. Rich comment JSON is portable
application data; it is not inserted into the edited document or interpreted
as HTML. A custom UI can render it with its own comment schema. The supplied
React panel presents its text projection.

## Anchors and document changes

An attached inline or block anchor records structural positions plus enough
portable context to recover from a replacement:

```ts
interface CommentAnchor {
  type: 'inline' | 'block' | 'document'
  status: 'attached' | 'orphaned'
  from?: number
  to?: number
  quote?: string
  prefix?: string
  suffix?: string
  nodeType?: string
  fingerprint?: string
}
```

For normal edits, transaction mappings move the anchor with the content. A
complete imported or synchronized document may not retain a usable mapping;
FountainJS then attempts deterministic quote/context or block-fingerprint
recovery. It does not guess when candidates are equally strong. The thread
becomes `orphaned`, remains in the store, and can be attached to a deliberate
new selection with `reattachCommentThread`.

Mapped anchor changes are sent to the adapter as `update-anchor` operations.
When disconnected they are queued and flushed after reconnection. Transactions
identified as remote by the collaboration extension do not echo another anchor
operation; the origin client persists the mapped anchor through the shared
comment store.

Anchors are document-relative metadata rather than marks in the document.
Comments therefore do not appear in exported HTML, Markdown, JSON, or text
unless the application deliberately exports its separate comment records.

## State, selection, hover, and events

```ts
const state = getCommentsState(editor)
// status, threads, selectedThreadId, hoveredThreadIds,
// pendingThreadIds, and an optional bounded error

const unsubscribe = subscribeCommentEvents(editor, event => {
  if (event.type === 'anchor-orphaned') notifyReviewer(event.thread.id)
})

selectCommentThread(editor, threadId)       // also selects its anchor by default
unselectCommentThread(editor)
hoverCommentThreads(editor, [threadId])
```

Events cover thread creation/update/removal, selection, hover, anchor orphaning
and restoration, and contained adapter errors. Event listeners are
observational: a listener exception cannot corrupt editor state.

`pendingThreadIds` indicates operations waiting for an authoritative adapter
response. FountainJS does not optimistically mutate a thread. This avoids
showing a comment as saved when the backend rejected it or returned a newer
revision.

## Production adapter contract

An adapter receives a small host-facing context:

```ts
interface CommentsAdapter {
  connect(context: CommentsAdapterContext): void | Promise<void>
  apply(operation: CommentOperation): CommentAdapterResult | Promise<CommentAdapterResult>
  disconnect?(): void | Promise<void>
  destroy?(): void
}
```

`connect` loads the current snapshot with `context.replaceThreads(threads)` and
subscribes to authoritative changes. It can publish transport state through
`context.setStatus`. `apply` persists one atomic operation and returns the
authoritative updated `thread`, or `removedThreadId` for deletion.

A typical authenticated adapter has this shape:

```ts
function commentsAdapter(roomId: string): CommentsAdapter {
  let stop: undefined | (() => void)

  return {
    async connect(context) {
      const response = await fetch(`/api/rooms/${roomId}/comments`, {
        credentials: 'include',
      })
      if (!response.ok) throw new Error('Could not load comments')
      context.replaceThreads(await response.json())

      stop = subscribeToRoomComments(roomId, threads => {
        context.replaceThreads(threads)
      })
    },

    async apply(operation) {
      const response = await fetch(`/api/rooms/${roomId}/comments/operations`, {
        method: 'POST',
        credentials: 'include',
        headers: { 'content-type': 'application/json' },
        body: JSON.stringify(operation),
      })
      if (!response.ok) throw new Error('Comment change was rejected')
      return response.json()
    },

    disconnect() { stop?.(); stop = undefined },
  }
}
```

The server should:

1. authenticate the actor independently of `operation.actor`;
2. authorize the room, thread, and exact operation;
3. validate IDs, timestamps, content, metadata, anchors, and size limits;
4. deduplicate `operationId` so a retry is idempotent;
5. serialize or reject conflicting revisions and return the authoritative
   result; and
6. publish the resulting snapshot or operation only to authorized subscribers.

`reduceCommentOperation(threads, operation)` is a pure reference reducer useful
inside a trusted local adapter, worker, test, or server implementation. It is
not authentication or access control.

## Permissions and trust

`CommentPermissions` controls whether the current interface exposes an action:

```ts
const comments = createCommentsExtension({
  adapter: () => commentsAdapter(room.id),
  user,
  permissions: {
    createThread: ({ user }) => user.role !== 'viewer',
    resolveThread: ({ user, thread }) =>
      user.role === 'editor' || thread?.author.id === user.id,
    deleteThread: ({ user }) => user.role === 'owner',
  },
})
```

By default anyone represented by the local integration may create, reply,
react, and resolve. A comment author may edit or delete that comment. A thread
author may archive, delete, or reattach that thread. These defaults are UI
policy only. Browser code and incoming author metadata are untrusted; the
adapter service must enforce the real policy using its authenticated session.

Avatar URLs pass FountainJS URL policy before entering state. Snapshots and
operations are normalized, cloned, frozen, bounded, and rejected on malformed
IDs, timestamps, positions, or non-serializable data. Render comment content as
text or through a safe schema renderer—never assign it to `innerHTML`.

## React panel

Install React only when the product wants the supplied renderer:

```tsx
import { FountainComments } from 'fountainjs-editor/react/comments'

<FountainComments
  editor={editor}
  title="Article review"
  reactions={['👍', '✅', '❓']}
  showArchived={false}
  onError={reportCommentError}
/>
```

The panel exposes labelled thread targets, a live thread list, keyboard-native
forms and buttons, selection state through `aria-pressed`, pending status,
errors through `role="alert"`, and the full supported thread lifecycle. It is a
replaceable surface over the same public APIs; DOM, Web Component, Vue, Svelte,
and Angular products can subscribe and render their own interface.

## Using comments with Yjs

Document collaboration and discussion storage are independent:

```ts
const kit = composeExtensions([
  CoreExtension,
  createYjsCollaborationExtension({ document: ydoc, provider, user }),
  createCommentsExtension({ adapter: () => commentsAdapter(room.id), user }),
])
```

Yjs synchronizes the document and relative presence. The comments adapter
synchronizes thread records and mapped anchors. They may use the same network
service, separate services, a CRDT-backed map, or no network at all. Every
client in the room must still use a compatible Fountain schema.

## Lifecycle and testing

`connectComments`, `disconnectComments`, and `reconnectComments` are available
as functions and composed commands. Destroying the editor unsubscribes state,
disconnects the adapter, calls its optional `destroy`, and removes listeners.

For product tests, use `InMemoryCommentsStore` to connect two editors without a
network. Test server authorization separately, then exercise one real adapter
route for initial load, create/reply, a conflict, reconnect, and deletion. The
repository's browser suite operates the same package exports used by consumers
and verifies shared annotations plus the React workflow in Chromium, Firefox,
and WebKit.
